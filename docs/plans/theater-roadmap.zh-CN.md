# 剧场化改造路线图（P0–P4）

> 状态：P0、P1、P2 已完成（见 §3–§5）；P3、P4 待实施。所有文件路径、接口名以当前代码为准。

## 0. 目标与范围

**目标**：让世界从"角色之间的聊天"变成"有结果、有意外、有舞台感的演绎"。

**本期范围**

| 阶段 | 内容 | 解决的问题 |
|---|---|---|
| P0 | 骰子判定 + 五档结果 | 行动没有意外，想做的都能做成 |
| P1 | 说书人 + 剧场视图 | 读起来像日志，不像戏 |
| P2 | 属性与专长 | 骰子缺少依据，人物能力没有区别 |
| P3 | 金钱与交易（存款为草案） | 世界里没有可争夺的资源 |
| P4 | 天气状态机 + 事件牌堆 | 世界不会自己变化 |

**不在本期**：附身/角色扮演（原 P5）、名著演绎（角色卡、剧情锚点、人物语料）、收支循环（工资、伙食、房租）、技能成长、多币种、分区域天气、室内/室外区分。

## 1. 现状基线

两个示例世界的动作统计（`examples/snapshots`，全部动作记录）：

| 世界 | 动作总数 | 说话 + 传信 | 肉体行动 | 肉体行动成功率 |
|---|---|---|---|---|
| 玄武门之变 | 237 | 147（62%） | 15 | 15/15 |
| 谁是内鬼 | 204 | 98（48%） | 6 | 5/6 |

根因（详见上一轮分析）：

1. 角色状态里没有可计量的资源，说话成了最划算的行动。
2. 成败由 LLM 定性裁定，没有随机性：
   - `engine/executors/physical.py` 和 `engine/executors/covert.py` 的裁判直接输出成败；
   - `engine/executors/work.py` 由角色第一人称自评。
3. 没有把一步写成一场戏的叙事层，前端叙事流是逐条的动作记录。

**基线测量（每个阶段完成后对比）**

- 指标：动作类型分布、各类型成功率、五档结果分布（P0 起）、单世界 token 消耗。
- 方式：用同一预设和同一主题跑 30 步，从快照里统计。

这些统计都是客观计数，做成 `tuning/` 下的一个脚本即可，不需要调用 LLM。

## 2. 贯穿全程的约束

每个 PR 都要满足下面这些约束。它们大多来自 `CLAUDE.md`，这里写明在本路线图里的具体含义。

1. **骰子是"世界物理"，不是认知。**
   - "难度与描写是主观的，交给 LLM；比大小是客观的，交给代码"，符合设计原则 5 的 LLM/规则分界。
   - 所有角色用同一套规则，不按主角/配角分支。
2. **数字只在代码层。**
   - 点数、难度值、属性分、天气状态码只进 API 和前端。
   - 进入角色 prompt、记忆和对白的只能是自然语言，比如"身手出众""险些失手""雨下得正紧"。
   - **例外是金额**：钱数本身是叙事事实（"三十两银子"），可以进入叙事层。
3. **LLM 用序号引用，类别由槽位决定**（IndexedRef，Prompt 设计原则 §6）。
4. **输出字段按依赖排序**：理由在前，结论在后；生成前提（选谁、选哪个能力）在内容前（§5、§5b）。
5. **每个文本字段声明长度上限**，重算 `output_budget` 并在调用处写出估算过程。
6. **判定链任一环失败就是空步**：`adjudication_failed=True`，不伪造结果（Rule 1 第 1 档）。
7. **Prompt 拆成 system 和 user 两段**：system 放跨调用不变的内容，user 放每次变化的内容（前缀缓存）。
8. **每个 PR 自带测试**，`pytest tests/ -x -q` 和 `ruff check .` 通过才算完成。

## 3. P0 骰子判定

### 3.1 规则

**骰子：3d6**（3–18，钟形分布）。

不用 d20：d20 是均匀分布，极端结果和中间结果一样常见，名将会频繁失手；钟形分布让"强者大概率表现得像强者"。

**难度（DC）**

| 难度 | 容易 | 普通 | 困难 | 极难 |
|---|---|---|---|---|
| DC | 8 | 11 | 14 | 17 |

**修正值**

- 修正值分两部分：
  - 能力修正由代码按属性和专长计算（见 §5）：行动者属性（等级 − 3）+ 专长等级 − 对手属性（等级 − 3）；
  - LLM 给出"情境"五档：明显劣势 / 略处劣势 / 相当 / 略占优势 / 明显优势，对应 −2 / −1 / 0 / +1 / +2，只计能力之外的处境（伤势、人数、器械、防备、地形）。
- P0 时还没有属性，"优势"五档对应 −4 / −2 / 0 / +2 / +4，综合人设所体现的能力和现场条件；P2 起改为上面的拆分。

**档位**：以 `余量 = 3d6 + 修正 − DC` 划分。

| 余量 | ≥ +5 | +1..+4 | −1..0 | −5..−2 | ≤ −6 |
|---|---|---|---|---|---|
| 档位 | 大成功 | 成功 | 成功但有代价 | 失败 | 大失败 |

**概率表**（3d6 全部 216 种组合穷举，单位 %，顺序为 大成功/成功/有代价/失败/大失败）

| 难度 \ 修正 | −3 | 0 | +3 |
|---|---|---|---|
| 容易 8 | 5/33/25/33/5 | 26/48/17/9/0 | 62/33/4/0/0 |
| 普通 11 | 0/9/17/48/26 | 5/33/25/33/5 | 26/48/17/9/0 |
| 困难 14 | 0/0/4/33/62 | 0/9/17/48/26 | 5/33/25/33/5 |
| 极难 17 | 0/0/0/9/91 | 0/0/4/33/62 | 0/9/17/48/26 |

旋钮只有一处：阈值、DC 和修正档位集中在一张常量表里，调参只改这一处，并由穷举测试锁住概率。

**何时不掷骰**：裁判先判断 `needs_check`。没有悬念的事（写一封信、搀扶一个不反抗的人）直接成功、不掷骰、不产生判定记录。跑团的原则是"只在失败有意思时才掷骰"，这样骰子出现时才有分量。

**纯运气**：赌局、彩票、抽签由裁判标 `pure_chance=true`，此时忽略优势修正，只按难度（相当于中签概率档）掷骰。

### 3.2 判定流程

由原来的"一次裁决"改为三段：

```
① 定难度（LLM，功能性裁判）→ ② 掷骰（代码）→ ③ 演结果（LLM，即现有的裁决/叙述 prompt）
```

**① 定难度**

新增 `engine/check.py` 中的 `CheckAssessor`，一次调用：

- 输入：行动者人设与状态、目标、现场（含在场者）、意图。与现有裁判看到的材料相同，复用 `assemble_scene_context`。
- 输出 JSON（按依赖排序）：

  ```json
  {"reason": "≤80字，权衡了什么", "needs_check": true, "pure_chance": false,
   "difficulty": "easy|normal|hard|very_hard", "edge": "much_worse|worse|even|better|much_better"}
  ```

- 估算：reason 80字≈120 + 四个枚举/布尔≈12 + 结构≈25，约 160 tok。

**② 掷骰**

- `resolve_check(difficulty, modifier, rng) -> CheckRecord`，纯函数。
- 随机源：`random.Random(f"{world_id}:{step}:{execution_id}")`。种子做法与调度器（`engine/scheduler.py`，种子是 `world_id`）一致，同一世界同一步可复现。

**③ 演结果**

各执行器现有的裁决 prompt 改为"结果已定，你来写"：

- user 消息末尾加【已定结果】段，用自然语言写档位：
  - "做成了，但付出了代价或留下了隐患——由你据实写出是什么"；
  - "不但没做成，还把局面弄糟了——由你据实写出糟在哪里"。
- 输出里删掉 `success` / `achieved` / `detected` 等成败字段，由代码从档位推出（不再让 LLM 判第二次）。
- 损耗、物件状态、处境等字段保留，prompt 要求与档位一致（比如大成功的打击伤害更重）。
- 删字段后重算各处 `output_budget`。

**失败处理**

- ① 或 ③ 调用失败：返回 `adjudication_failed=True` 的空步，掷出的骰子作废，不写任何东西。
- `needs_check=false`：跳过 ②，③ 照常写结果，档位按"成功"处理，不产生 `CheckRecord`。

### 3.3 各动作类型的映射

**PHYSICAL**

| 档位 | 结果 |
|---|---|
| 大成功 / 成功 | `succeeded=True` |
| 有代价 | `succeeded=True`，叙述里必须写出代价（自伤、惊动旁人、东西受损……） |
| 失败 / 大失败 | `succeeded=False`；大失败可伴随行动者自损或局面恶化 |

对人行动时，"优势"本身就是双方实力对比，不另做对抗掷骰。

**COVERT**：两个布尔值从同一个档位推出。"是否有人可能察觉"由代码按现场在场者客观判断。

| 档位 | 有潜在察觉者时 | 无人可察觉时 |
|---|---|---|
| 大成功 | 探到，且有额外收获，未被察觉 | 同左 |
| 成功 | 探到，未被察觉 | 同左 |
| 有代价 | **探到，但被察觉** | 只探到一部分 |
| 失败 | 没探到，未被察觉 | 同左 |
| 大失败 | **没探到，且被察觉** | 没探到，并留下痕迹 |

**WORK**

- 难度由功能性裁判（①）判定；结果仍由角色第一人称书写（③，保持沉浸）。
- 档位对应：超出预期 / 完成 / 完成但有瑕疵或多耗了工夫 / 没做成（可有部分进展）/ 搞砸了（材料损坏等）。
- 同步更新 `WorkExecutor` 类文档中"诚实自评"的描述。

**不掷骰的类型及原因**

| 类型 | 原因 |
|---|---|
| TALK | 对方是有意志的角色，成败由对方在角色内的回应决定；掷骰会替对方做决定。口才在 P2 以人设文字进入对白生成。 |
| SEND_MESSAGE | 投递本身没有悬念。 |
| MOVE | 路程时间由地图决定；P4 的天气会影响路程。 |
| REST | 没有悬念。 |
| ERRAND | 跑腿者没有意志，可行性由规则判定。 |

## 4. P1 说书人与剧场视图

### 4.1 定位：只读、旁路、可以失败

- 说书人**不写任何角色状态**，它的文字**不进入任何角色的 prompt 和记忆**。所以它可以是全知视角，不会破坏信息不对称。
- 要加一条守卫测试：`agent/` 和感知链路不引用说书人的输出。
- 它在后台运行，不阻塞模拟步进。失败只意味着这一步没有剧本，模拟照常。

### 4.2 输入

- 本步的展示记录：动作结果、对白原文（`dialogue`）、内心独白（`inner_monologue`，记录里已有）、判定档位、事件和广播、死亡。
- 世界时间；P4 之后加上天气。
- 说书人自己维护的"前情提要"（≤100 字）。这是说书人的状态，不是角色的状态。

### 4.3 分幕分场（代码规则）

- **场**：按地点分组。同一地点、出场人物与上一步有重叠，就延续为同一场。只有未执行、进行中这类无事发生记录的地点不出场。
- **幕**：跨日、高烈度事件注入、有人死亡时换幕。
- 场号和幕号由代码分配，LLM 不参与。

### 4.4 输出（每步一次调用）

```json
{"scenes": [{"location_index": 1,
             "stage_direction": "≤60字 舞台提示：光线、声响、人物站位",
             "beats": [{"kind": "narration", "text": "≤80字"},
                       {"kind": "line", "line_index": 3},
                       {"kind": "aside", "monologue_index": 2}]}],
 "memo": "≤100字 前情提要"}
```

- **台词一律引用原文**（`line_index` / `monologue_index`，IndexedRef），说书人不重写台词。理由：
  - 保真：角色说过的话是唯一可信的记录；
  - 省 token；
  - 杜绝"说书人替角色说了没说过的话"。
- 说书人只写舞台提示和旁白，旁白把动作和判定结果编进叙事。
- 规模上限：每步最多 4 场，每场最多 8 拍，其中旁白最多 3 拍。
- 估算：每场 地点 3 + 舞台提示 90 + 3 条旁白×125 + 5 条引用×10 + 结构 30 ≈ 550 tok，×4 场 + memo 150，约 2.4k tok。实现时按最终字段重算。
- 约束：
  - 复用 `CLOSED_WORLD_FACT_RULE`，不得新增记录里没有的事实；
  - 不写 id，不写"第N步"；
  - 角色用名字和性别称呼（`person_referent`）。

### 4.5 运行与存储

- **模块**：`engine/stage_narrator.py` 的 `StageNarrator`。
  - 不放进 `engine/narration.py`：那个文件是执行器用的措辞约定。
- **调度**：步结束、快照保存后入队。单个后台工作者按步序处理（前情提要需要顺序）。若积压，模拟不等它。
- **存储**：`SnapshotProvider` 增加 `save_narration` / `load_narration`，内存版和文件版都要实现。`delete_steps_after` 一并删除对应剧本，保证重置世界时剧本不残留。
- **模型路由**：新增 `LLMScene.STAGE_NARRATION`，可以单独路由到文笔更好的模型。trace 新增 `Stage.NARRATION`。

### 4.6 API 与前端

- **API**：
  - `GET /worlds/{id}/narration?from=&to=`；
  - WebSocket 新增 `narration` 消息；
  - 回放路径读取已存剧本；没有剧本的旧世界回退到现有叙事流。
- **前端**：
  - `views/WorldView` 增加「记录 / 剧场」切换；
  - 新建 `components/theater/`：幕/场标题（地点 · 时间）、斜体舞台提示、旁白、台词（说话人用身份色）、独白（旁白样式）；
  - **追光**：播放某一场时，`MapStage` 把镜头推到该地点，其余区域压暗。夜间整体压暗用现有天气渲染里的 `dark`。
- **可选 PR 1.5**：命令行 `python main.py narrate <world_id>`，为已有世界补生成剧本（需要 key）。

### 4.7 测试清单

- 分幕分场规则单测（延续、换场、换幕三种情况）。
- 引用序号越界或重复时丢弃（`IndexedRef`）。
- prompt 里没有 id 和步号，复用 `test_narrative_id_leak_guard` 的做法。
- 调用失败时不落盘，也不影响步进。
- provider 的保存、读取、删除；API；前端视图测试。

  - 任意一步都能作为剧本阅读；
  - 抽查剧本时，找不到记录里没有的事实；
  - 可选：在 `tuning` 加一个审查维度，评"剧本对记录的忠实度"。

## 5. P2 属性与专长

### 5.1 设计

**五项通用属性**（与题材无关，满足 Rule 7），1–5 级：

| 属性 | 涵盖 |
|---|---|
| 体魄 | 力量、耐力、抗打击 |
| 身手 | 敏捷、潜行、手上功夫 |
| 心智 | 学识、谋算、洞察 |
| 口才 | 说服、欺瞒、交涉 |
| 胆识 | 意志、镇定、威慑 |

- 等级用词：1 孱弱 / 2 平平 / 3 寻常 / 4 出众 / 5 超群。修正值 = 等级 − 3，即 −2..+2。
- **专长**：每人最多 4 项，名称 ≤6 字（"剑术""医术""算学"），1–3 级（略通 / 精熟 / 宗师），修正 +1..+3。

### 5.2 生成：整体校准调用

- 新增 `world/builders/ability_designer.py` 的 `AbilityDesigner`，放在 `AgentGenerator` 之后。
- 一次调用看到全部人设，统一给出所有人的属性和专长。不能逐人生成的原因：人设是每人一次并行调用生成的，看不到其他人，无法横向校准（谁力气最大、谁最聪明）。
- prompt 约束：
  - 3 级是普通成年人；5 级是当世顶尖；
  - 主角不自动高分；
  - 每人至少一项短板。
- 每人的输出：序号（生成前提）→ 依据（≤30 字，擅长什么、短在哪）→ 属性 → 专长。
- 估算：8 人 ×（依据 45 + 属性 40 + 专长 4×17 + 结构 20）≈ 1.4k tok。按 Rule 2：重试一次，仍失败就抛错。

### 5.3 存储

- `SoulLayer` 增加 `attributes` 和 `skills`。它们属于不可变身份，建世界时固定，运行时不变。
- `AgentDefinition.soul_data` 和 `from_dict` 读写这两个字段。
- 没有这两个字段的旧世界按"全部 3 级、无专长"处理（修正为 0），只有一条代码路径，不做兼容分支。

### 5.4 接入判定

- `CheckAssessor` 的输入增加行动者的能力清单（编号，用词不用数字）；对抗性行动再附上对手的能力清单。
- 按 §6 的扁平槽位，输出三个序号槽：
  - `attribute_index`：行动者用哪项属性；
  - `skill_index`：用哪项专长，0 表示不用；
  - `opposing_attribute_index`：对手用哪项属性抵抗，0 表示无对抗。
- 越界序号视为"未填"。
- 修正值 = 行动者属性修正 + 专长加值 − 对手属性修正 + 情境修正（LLM 给 −2..+2）。
- `edge` 字段收窄为情境修正。

### 5.5 认知侧

- `PersonalityLayer.to_prompt_context` 增加一行，只用文字，例如「所长：剑术精熟、口才出众；所短：体魄孱弱」，让决策更贴合角色能力。
- 他人的能力不出现在任何角色的 prompt 里（信息不对称）。

### 5.6 前端、测试与 PR

- **前端**：`CharacterCard` 显示属性条和专长标签；建世界后的审阅界面同步显示（只读）。
- **测试**：
  - 设计器解析与重试；
  - 持久化往返；
  - 修正值计算；
  - 越界序号；
  - 人设文本里没有能力数字；
  - 旧世界加载。
- **PR 拆分**：
  - PR 2.1 数据模型 + `AbilityDesigner` + 持久化；
  - PR 2.2 接入判定与人设文本；
  - PR 2.3 前端。
- **成本**：建世界多 1 次调用；运行时每个人设块多约 30 tok。

## 6. P3 金钱与交易

### 6.1 表示：钱是一种"可分的物品"

- 新增 `WorldEntityType.MONEY`，`WorldEntity` 增加 `quantity`（仅 MONEY 有意义）。
- 选它而不选"每人一个余额数字"的原因：现有物品机制可以全部复用。钱能被抢（SEIZE）、被递交（RELINQUISH）、掉在地上、被跑腿带走，旁人能看见钱袋易手，暗中行动能发现藏钱处——这些裁决和感知链路都是现成的。
- 余额数字的方案需要给每一种机制另开一条通道。

### 6.2 建世界时的经济设定

- `ThemeAnalysis` 增加 `economy`：
  - 货币名（"银子"）、单位（"两"）；
  - 不超过 6 条参考物价（名称 ≤10 字，价格为整数）。
- 由 `ThemeAnalyzer` 现有调用一并输出，并重算 token 预算。
- 每人的初始现金由 P2 的整体校准调用增加 `cash` 字段，与家境一起横向校准。初始化时为每人生成一份 MONEY 实体（金额为 0 则不生成）。
- 参考物价是世界级常量，放进决策和裁判 prompt 的 system 段，不影响前缀缓存。

### 6.3 环境机制

- `EntityStateChange.quantity: int | None`：对 MONEY 只移动这么多。`EnvironmentSystem.change_entity_state` 负责拆分和合并。
- 不变量：每个持有者、每个地点最多一堆 MONEY；数量归零则移除。
- **金额的信息不对称**：
  - 自己的钱和地上的钱显示具体数目；
  - 别人手里的钱只显示"一只钱袋"。
  - 做法与 `WorldEntity.readable_by` 同一思路，在 `VisibleEntity` 和 `render_entity` 中体现。
- 存档、API 和前端物品展示都带上 `quantity`。

### 6.4 肉体行动中的钱

- 决策新增槽位 `physical_amount`：只在选中 MONEY 实体时有意义。
- 裁判输出 `amount_moved`，不超过可用金额，由代码截断（数值截断属于字段级矫正）。
- 抢钱由 P0 判定成败与数额，档位影响抢到多少。
- 跑腿带钱：`ErrandOrder` 增加 `amount`。

### 6.5 交易动作 TRADE

**为什么要新增动作类型**（Action Type Rules）：双方同意、原子、双向的所有权交换，是现有类型做不到的效果。TALK 不能转移东西，PHYSICAL 的递交是单向的，也没有议定条件。

**决策槽位**

| 槽位 | 含义 |
|---|---|
| `trade_person_index` | 交易对象 |
| `trade_give_entity_index` / `trade_give_amount` | 我付出什么（必须是我持有的物品或钱） |
| `trade_ask_entity_index` / `trade_ask_amount` | 我想要什么（必须是对方持有的物品或钱） |

至少一侧不能为空；违反时由决策解析拒绝。

**执行器** `engine/executors/trade.py`：

- 一次调用：先写双方角色内的议价对白（≤4 轮，沿用 TALK 的对白约定），再给出成交判定：

  ```json
  {"dialogue": [...], "reason": "≤60字", "agreed": true, "final_give_amount": 0, "final_ask_amount": 0}
  ```

  对白是判定依据，所以排在最前（§5b）。
- 成交后，双向转移作为两条 `EntityStateChange` 一起落地，要么都成、要么都不成。
- 关系变化沿用"方向 → 固定幅度"的机制；双方记忆沿用 TALK 的写法。

**其他接入点**

- 不掷骰：对方是有意志的角色。口才通过人设文字影响对白。
- 仲裁：像 TALK 一样占用对方的回合。
- 契约：`frontend/src/lib/contract.ts` 增加 `trade`（契约对齐测试会检查）；`ActionRow` 和地图动作标签增加对应展示；lab 加一个交易场景。

### 6.6 存款（P3b，草案，P3a 跑一段时间后再定）

- 建世界时可以指定一个地点为钱庄/银行（`economy.bank_location_index`，可以为空）。
- 账本放在 `EnvironmentSystem`：每人一个存款余额，属于世界状态。
- 存取在银行地点进行。具体是复用"操作柜台"的肉体行动，还是新增动作，留到 P3a 之后决定。
- 自己的存款以文字进入自己的人设状态（"在钱庄存着约两百两"）。
- 抢银行等于抢银库地点的 MONEY 实体，不需要新机制。

### 6.7 彩票与赌局

- 用 P0 的纯运气判定，加 P3 的金钱转移即可。
- 奖金来自"庄家/奖池"的 MONEY 实体，不凭空造钱，以免通胀。

### 6.8 测试与 PR

- **测试**：
  - 拆分/合并不变量；
  - 部分抢夺；
  - 递交；
  - 金额的信息不对称；
  - 交易槽位校验；
  - 交易的原子性（要么都转、要么都不转）；
  - 存档往返；
  - 契约对齐。
- **PR 拆分**：
  - PR 3.1 经济设定 + MONEY 实体 + 环境机制 + 展示；
  - PR 3.2 肉体行动与跑腿中的钱；
  - PR 3.3 TRADE；
  - PR 3.4 存款（待定）。
- **风险**：本阶段牵动面最大（环境、存档、决策、仲裁、API、前端）。按"整体影响"原则，动手前先列出全部受影响位置和需要更新的测试夹具。

## 7. P4 天气与事件牌堆

### 7.1 天气状态机

**状态**

- 种类：晴 / 阴 / 雨 / 雪 / 风。种类与前端已有渲染的 `rain` / `snow` / `wind` 对齐，雾暂不做。
- 强度：沿用 `Severity` 三档。
- 全世界共用一个天气，v1 不分区域。

**气候**

- 建世界时由 `ThemeAnalyzer` 从封闭集合中选一种：温带季风 / 湿润亚热带 / 干旱 / 寒冷 / 热带。未知值矫正为默认值。
- 季节由世界日历的月份推出。

**转移**

- 新增 `engine/weather.py` 的 `WeatherSystem`。
- 每 3 个世界小时按"气候 × 季节"的转移表推进一次（纯规则，带种子）。推进间隔按世界秒计，与 `seconds_per_step` 无关。

**存储**：快照 `metadata["weather"]`，恢复时读取。

**效果**

1. **感知**：情境里加一行天气，例如「外头下着大雨」。
2. **转变提示**：天气明显转变时，向所有地点投递一条环境观察（代码模板，不调 LLM）。
3. **裁判**：`assemble_scene_context` 加入天气，难度评估会把它算进去（雨夜潜行容易、追逐更难）。
4. **移动**：大雨、大雪时路程时间 ×1.25 / ×1.5，在 `MovementExecutor` 中计算。
5. **前端**：`StepEvent.weather` 交给 `phaser/weatherPlan.ts` 持续渲染；按时辰压暗作为舞台灯光。

**已知限制**：地点没有室内/室外区分，v1 所有人都能感知天气。

### 7.2 事件牌堆

- **生成**：建世界时多一次调用，生成 12–20 张与本世界相符的事件牌：

  ```
  {标题 ≤12字, 梗概 ≤40字, 范围: 局部/全局, 烈度, 权重 1–3, 前提: 天气/时段（可空）}
  ```

  牌堆是本世界的数据，随世界存储，满足 Rule 7（题材内容不进通用代码）。
- **抽牌**：在 `EventSystem` 现有的规则闸门里，用种子随机数按权重决定抽不抽、抽哪张。
  - 只有满足前提的牌才进入候选；
  - 抽过的牌在冷却窗口内不再抽；
  - 抽牌记录进入 `InjectionLedger`，恢复世界后保持一致。
- **落地**：抽中时跳过"要不要注入"的 LLM 闸门（骰子已经决定了），把这张牌交给现有的计划生成，由 LLM 决定落在谁身上、在哪里、怎么说，再走现有通道投递。没抽中则保持现在的行为。配额限制不变。

### 7.3 测试与 PR

- **测试**：
  - 转移表每行概率之和为 1；
  - 种子可复现；
  - 存档往返；
  - 感知中出现天气行；
  - 移动倍率；
  - 抽牌可复现、冷却、前提过滤；
  - 计划 prompt 包含牌面梗概，且没有 id。
- **PR 拆分**：
  - PR 4.1 天气系统与感知、裁判、移动接入；
  - PR 4.2 前端持续天气与灯光；
  - PR 4.3 事件牌堆。
- **成本**：天气不调 LLM；牌堆在建世界时多 1 次调用；运行时抽中的牌会替代一部分 LLM 闸门调用。

## 8. 顺序与依赖

```
P0 骰子 ──→ P2 属性（修正值改为来自属性）
   │
   └──→ P3 金钱（抢钱判定、纯运气）
P1 说书人：独立，可与 P0 并行；有 P0 后旁白能写判定结果
P4 天气/牌堆：独立；天气会进入 P0 的难度评估
```

**建议顺序**：P0 → P1 → P2 → P3 → P4。P4 与其他阶段互不依赖，人手允许时可以提前。

**每个阶段的完成标准**

- 单测和集成测试通过，`ruff check .` 通过；
- 用一个便宜的预设跑 10–30 步，与基线指标对比；
- 更新相关文档（配置项变化时更新 `docs/configuration*.md`）和 `CHANGELOG.md`。

## 10. 风险与对策

| 风险 | 对策 |
|---|---|
| 名人频繁失手，不像原著 | 钟形分布 + `needs_check` 过滤无悬念的事 + 优势修正；阈值集中在一张表里便于调整 |
| 两段裁决增加延迟 | 难度调用很短；同一步内的裁决本来就是并发的（`finalize_executions_batch`） |
| LLM 写结果时无视档位 | 档位放在 user 消息末尾，靠近生成点；调优阶段加"结果与档位一致"的检查 |
| 说书人编造事实 | 台词只引用原文，加封闭世界规则；可选的忠实度审查 |
| 测试改动面大 | 统一的夹具 `fixed_assessor(tier)`；P0 先做纯函数，再逐个接入执行器 |
| 经济失衡 | 除建世界和奖池外不造钱；收支循环不在本期 |
| 存档格式变化 | 项目处于早期，不保证向后兼容；新字段都带默认值读取 |
